## Rules specific to M3

- **Where things live.** Pure model code in `src/meta/` (profile, Foundry rules, settings data, unlocks) and `src/save/` (codec, store, scheduler, migrations, snapshot container). Both are `RefCounted` only, enforced by `tools\lint.ps1`: no `Node`, `Input`, `OS.`, `DisplayServer`, `randf`, and **none of the autoload words `Game Profile SaveManager Content Services Clock Events Log` as identifiers** (the lint regex is a word match, so `class_name Profile` or a variable `clock` typed `Clock` fails). Use `PlayerProfile`, `ClockSource`, `SaveService`. Disk and wall-clock glue lives in `src/core/` (`DiskSaveFs`, `SystemClock`, `SaveService`), UI in `src/ui/`.
- **No new autoloads.** TECH_ARCHITECTURE 1.3 lists `Profile`, `SaveManager` and `Clock` as autoloads. We do not add them (`project.godot` is a shared file and the layer lint forbids the words). Instead `Game` owns `profile: PlayerProfile`, `saves: SaveService`, `clock: ClockSource`, exactly like it owns `audio`. M3-20 writes this into TECH_ARCHITECTURE as a changelog line.
- **Sim stays pure and deterministic.** Foundry effects enter the sim only as data in `SimConfig` (`foundry_levels`, `foundry_f`), recorded in the `RunRecord` so replays stay valid. With all Foundry levels 0 every hash is unchanged: **no `SimVersion` bump in M3** and `tests/sim/test_replay.gd` goldens must not change (every task that touches `src/sim` quotes `git diff --stat -- tests/sim/test_replay.gd` empty). If a task finds it cannot keep the goldens, it stops and reports; an intentional bump needs the main agent's approval, a `SimVersion.CURRENT` increment, refreshed goldens and a note in `docs/tasks/M3.md`.
- **Save-shape rule (CLAUDE.md):** any change to the serialized shape after M3-04 lands is a schema bump plus a migration plus a fixture.
- **Never silently wipe a save.** A damaged or too-new save is never overwritten without an explicit player action, and the damaged bytes are kept (`*.corrupt`).
- **Buying** is tap = 1 level on release, hold = accelerating repeat (`RepeatBuyModel`: first repeat 0.35 s, 250 to 50 ms over 2 s, steps of 10 after 3 s and 100 after 6 s). No buy-mode selector anywhere. The Foundry uses the same model and the same `AudioHooks.buy_step` / `buy_end` / `deny`.
- **Strings only via `data/strings_en.csv`** (M3-11 adds every M3 key up front so the UI tasks never edit the CSV; a UI task that finds a missing key stops and tells the main agent). **UI style** is the V1 kit: `ThemeBuilder`, `UiKit`, `Palette`, fonts, `SafeArea`, `LayoutMode`. Sizes are in 1080-wide base pixels (body text at least 38 px, touch targets at least 148 px).
- **Part B rules.** Frames are data (`data/frames.csv`) entering the sim only as `SimConfig.frame` modifiers recorded in the run record; **VANGUARD is neutral, so goldens, replays and `SimVersion` stay untouched** (same quoting rule as the Foundry). Frame passives are pure sim code with unit tests. The title art starts with a style frame and a **user gate** (`M3-TITLE-GATE`); no production art or title scene work (M3-26 to M3-28) starts before approval. The title stays within about 15 draw calls and obeys `VisualQuality` (LOW: 1 smoke layer, no embers).
- **Never use MultiMesh `use_colors`/`use_custom_data`** (CLAUDE.md gotcha); M3 adds no MultiMesh, but the Home diorama must not introduce one.
- **Audio agent in flight.** An audio agent is editing `src/audio/`, `assets/audio/`, `tools/audio_gen/` and small hooks in `src/ui/` (results tally sound: `main.gd`, `results_overlay.gd`) until it finishes. Waves 1 and 2 below touch none of those paths. UI waves (3+) start only after the main agent confirms the audio agent is done. M3 only reads `AudioSettings` (`to_dict`/`from_dict`/`apply`) and calls `AudioHooks`; it never edits `src/audio/`.
- **Importer runs** (`tools\import_data.ps1`) write `src/data_gen/`: never run two at once. Only M3-05 and M3-11 run it.
- **(impl) markers:** every choice not in the GDD is marked **(impl)** in the commit message; the main agent folds them into the GDD or `09_open_questions.md` (candidate list at the end of this file).
- **Commit/CI:** commit only when the user asks; after any push the main agent watches GitHub Actions to green (CI file `docs/setup/ci.md`).

## HMAC key decision (flagged, already made in TECHARCH)

TECH_ARCHITECTURE 5.1 decided: the HMAC-SHA256 key is **embedded in the client and obfuscated** (split across constants, assembled at runtime). That is obfuscation, not security: anyone who unpacks the APK or reads the repo can recompute the footer. The stated threat model is "stop casual editing (file edit, memory/file cheat tools), not a reverse engineer", and offline single-player progress is allowed to be cheatable; anything competitive or monetary is validated server-side (TECHARCH section 8, M7). M3 implements exactly that, and adds three guard rails (all **(impl)**):
1. The key is **not a secret and not in the "no secrets in git" category**: it is source, and the code and docs say so (`SaveKey` header comment).
2. `SaveKey.override(bytes)` exists so tests can use a test key and a release build may later load a per-build key from the ignored `secrets.local.json` (field `save_hmac_key`); M3 ships no such file and no CI secret.
3. The key is never reused for the backend (Nakama) or any server verification, and cloud save (M7) must not trust a client-signed blob for value (server-side shadow profile, TECHARCH 5.4/8).
The user may want a different decision (for example no HMAC, or a key that mixes in a device id); mixing a device id would break restore on a new device and cloud transfer, so the plan does not do it. Listed as 09 Q60 with the default.

## M3-01 SaveCodec and HMAC key
- **Status:** [x] DONE 2026-11-08 (dc4fc6f)
- **Goal:** the signed, compressed container for every persisted blob (profile and run snapshot): TECH_ARCHITECTURE 5.1.
- **Size:** M. **Group:** A. **Depends on:** none.
- **Files:** `src/save/save_codec.gd` (`class_name SaveCodec`), `src/save/save_key.gd` (`SaveKey`), `src/save/decode_result.gd` (`DecodeResult`), `tests/unit/save/test_save_codec.gd`.
- **Inputs:** `docs/TECH_ARCHITECTURE.md` section 5.1 and 5.2 (forward-compat rule), the "HMAC key decision" block above, CLAUDE.md (BigNum as strings).
- **Spec:**
  - Layout (little endian): `magic` 4 bytes (`ISAV` profile, `ISNP` run snapshot; the caller passes it), `schema_version` u16, `raw_len` u32, `payload_len` u32, then `payload_len` bytes of `PackedByteArray.compress(FileAccess.COMPRESSION_ZSTD)` of the UTF-8 JSON text (profile) or of caller-provided bytes (snapshot), then a 32-byte footer `Crypto.hmac_digest(HASH_SHA256, key, header + payload)`.
  - `SaveCodec.encode(magic: String, schema: int, raw: PackedByteArray) -> PackedByteArray`; `decode(magic: String, bytes: PackedByteArray, max_schema: int) -> DecodeResult` with `status` in `OK, TRUNCATED, BAD_MAGIC, BAD_HMAC, BAD_PAYLOAD, TOO_NEW` and `schema`, `raw`. Order of checks: length, magic, **HMAC first** (constant-time compare, manual loop), then lengths (`raw_len` capped at 16 MB against a decompression bomb), then decompress, then `TOO_NEW` when `schema > max_schema` (a newer file is still validly signed, so HMAC passes first and the status is precise).
  - `SaveKey`: 32 bytes assembled at runtime from at least 4 split, XOR-masked constants (obfuscation as decided, header comment says plainly "not a secret"). `SaveKey.bytes()` returns the current key, `SaveKey.override(b: PackedByteArray)` / `reset()` for tests and a future ignored release key.
  - Helpers: `encode_json(magic, schema, d: Dictionary)` and `decode_json(...)` returning `Dictionary` (JSON parse errors give `BAD_PAYLOAD`). JSON numbers that are ints stay ints on read (`int` fields are re-cast by the model, not here).
- **Acceptance:** tests: encode then decode returns the same bytes for sizes 0, 1, 1 KB, 300 KB; flipping any single bit at 20 positions (header, payload, footer) never returns `OK` (status is `BAD_HMAC` or `BAD_MAGIC`/`TRUNCATED`, never a crash); truncating at every length from 0 to 40 returns `TRUNCATED` or `BAD_MAGIC`; a payload whose HMAC is recomputed with a different key gives `BAD_HMAC`; a hand-built container with `schema = max_schema + 1` and a valid HMAC gives `TOO_NEW`; `raw_len` above 16 MB with a valid HMAC gives `BAD_PAYLOAD`; decode of 1,000 random byte strings never crashes; a 300 KB payload round-trips in under 50 ms (informational); `SaveKey.bytes().size() == 32` and `override`/`reset` restore it; a golden test pins the footer for a fixed key and payload (catches accidental format drift); lint clean (no forbidden words in `src/save/`).

## M3-02 SaveFs, atomic write, backup and fallback
- **Status:** [x] DONE 2026-11-08 (dc4fc6f)
- **Goal:** crash-safe persistence: TECH_ARCHITECTURE 5.1 and 2.8 "save on APPLICATION_PAUSED" rule (temp file, flush, rename, `.bak`), and a load that never wipes.
- **Size:** L. **Group:** A. **Depends on:** M3-01.
- **Files:** `src/save/save_fs.gd` (interface: `read(path) -> PackedByteArray` (empty = missing), `write(path, bytes) -> bool` (create or truncate, flushed and closed), `rename(from, to) -> bool` (replaces an existing target), `remove(path) -> bool`, `exists(path) -> bool`), `src/save/memory_save_fs.gd` (test double with fault injection: fail the Nth operation, or "power loss" after a given step), `src/core/disk_save_fs.gd` (`FileAccess`/`DirAccess` on `user://save/`; on Windows `DirAccess.rename` onto an existing file fails, so it removes the target first, and the load order below tolerates that window), `src/save/save_store.gd` (`SaveStore`), `src/save/load_result.gd` (`LoadResult`), `tests/unit/save/test_save_store.gd`, `tests/unit/core/test_disk_save_fs.gd`.
- **Inputs:** TECH_ARCHITECTURE 5.1, 5.2, 2.8; the M3-01 codec.
- **Spec:**
  - Names for a store `name` (`profile`, or `run_snapshot`): `<name>.sav` live, `<name>.bak` previous good, `<name>.tmp` in flight.
  - `SaveStore.new(fs, magic, max_schema)`. `save(schema, raw) -> bool` writes **tmp first**, flushes, **reads tmp back and decodes it** (a failed verify aborts, the live files are untouched), then: if `.sav` exists and decodes OK, `rename .sav -> .bak` (replacing the old backup; a damaged live file is **not** promoted to the backup), then `rename .tmp -> .sav`.
  - `load(max_schema) -> LoadResult` with `status` in `OK, FRESH, RECOVERED, CORRUPT, TOO_NEW`, `source` (`live`, `bak`, `tmp`), `schema`, `raw`. Order: `.sav`; on any failure `.bak`; then a valid `.tmp` (covers a crash between the two renames). `FRESH` only when **none** of the three files exist. If a file exists and every candidate fails: `CORRUPT` (or `TOO_NEW` when the best candidate decoded as too new). `RECOVERED` means a fallback was used: the caller shows a notice and re-saves.
  - `quarantine() -> bool`: renames every existing live/bak/tmp file to `<name>.corrupt` (numbered `.corrupt`, `.corrupt.1`, ... never overwriting a previous one); used only on an explicit player action (M3-14). `remove_all()` for the snapshot store at run end.
  - No `Time`, no `OS`; all file access through `fs`.
- **Acceptance:** tests on `MemorySaveFs`: save then load gives `OK` and the same bytes; second save leaves a `.bak` equal to the first payload; **power loss injected at every step** of `save` (after tmp write, after verify, after the first rename, after the second) leaves a store whose `load` returns `OK` or `RECOVERED` with either the old or the new payload, never `CORRUPT` and never a mix; live file with a flipped bit and a good `.bak` gives `RECOVERED` (source `bak`) and the corrupt live file is not copied over the backup by the next `save`; both damaged gives `CORRUPT` and both files are still present afterwards (nothing wiped, asserted); no files gives `FRESH`; a newer-schema file gives `TOO_NEW` and `save` is still possible only if the caller chooses (the store itself never deletes); a failing `write` or `rename` returns false and leaves the previous good state loadable; `quarantine` keeps all bytes under `.corrupt*` names and a second quarantine does not overwrite the first; `DiskSaveFs` test on `user://test_save_<pid>/` covers write/read/rename-over-existing/remove and cleans up; `SaveStore` never reads outside `fs`.

- **Spec:**
  - Fields: `data: BigNum`, `flux`, `cipher`, `merit: int` (all 0; no UI in M3), `foundry: Dictionary` (row id -> int level, only rows with level > 0 stored), `best_wave: Dictionary` (sector key `"1"` -> int; accessor `best_wave_s1() -> int`), `runs_total: int`, `run_counter: int` (starts at 0, +1 per started normal run), `last_banked_run: int` (id of the last banked run, -1 none), `lifetime_data: BigNum`, `farm_rate_1x: float` (EMA weight 0.4 of `data_run / game_minutes` over banked runs; 04 section 2.2), `settings: Dictionary` (opaque here, owned by M3-10), `frames_unlocked: Array[String]` (default `["vanguard"]`, never empty) and `frame_selected: String` (default `"vanguard"`, must be in `frames_unlocked`; an invalid value falls back to `vanguard` with a `load_errors` entry; part B; both are part of schema v1 and its fixture), `last_active_utc: int`, `device_id: String` (generated by the caller on first save, injected: `PlayerProfile` never calls a RNG), `created_utc: int`.
  - `begin_run() -> int` returns and increments `run_counter` (the run id). `bank_run(s: RunSummary) -> bool`: **idempotent per run id** (returns false and changes nothing when `s.run_id <= last_banked_run`), adds `data_run` to `data` and `lifetime_data`, raises `best_wave["1"]` to `max(best, s.death_wave)` for sector 1 only and only when `s.counts_for_progress` (debug-load runs set it false and bank nothing), increments `runs_total`, updates `farm_rate_1x`, sets `last_banked_run`. `RunSummary` carries `run_id, sector, death_wave, data_run: BigNum, kills, ticks, counts_for_progress`.
